# 战役复盘：某央企下属单位「三清单」与表元数据导入数据治理平台

> 开源脱敏版：单位、系统、人名、库名、路径均已泛化（系统 A/B/C、实例 INST1/INST2、Schema S1–S5），数字保留原值——对账方法靠的就是精确数字。

## 一句话

AI 按模板字面交了 5 版，平台 0 行成功；最后从平台导入记录和同事一份部分成功的文件里做数字对账，三组数字精确吻合，才发现「数据库名称(schema)」要填实例名、系统名要带单位前缀、判重忽略大小写。按此生成的新版：表 5,788 张、字段 117,277 个，恰等于平台两次历史成功数。

## 背景

- 任务：把三个系统（A、B、C）的三清单（数据资源清单、数据供给清单、负面清单）整合，再填进平台的「表元数据导入模板」（表信息、字段信息两个 sheet）上传，之后再导清单。
- 平台：多家外包拼出来的数据治理平台，规则不公开，没有测试环境。
- 用户原话：「这个系统……应该是多个外包进行拼凑的……每一种逻辑都不太相同，也是多次堆积成的屎山」「只求上传成功」。

## 对账：三组数字怎么对上的

| 平台数字 | 解释 | 吻合 |
|---|---|---|
| 同事版失败 7,800 | 她的表信息 5,787 行填了 Schema → 全败；字段信息填实例名，按**忽略大小写**数重复恰 2,013（精确口径只有 211） | 5,787 ＋ 2,013 ＝ 7,800 ✓ |
| 候选A 错误 129,455 条 > 失败行 126,648 | 多出来的 2,807 行各吃了第二条错误；候选A 按忽略大小写数重复：表 123 ＋ 字段 2,684 | 123 ＋ 2,684 ＝ 2,807 ✓ |
| 历史成功 5,788 与 117,277 | 按实例名、忽略大小写去重后：表 5,788、字段 117,277 | 两处都 ✓ |

得出的规则：
- **R1** 数据库名称填实例名（INST1/INST2），不是 Schema。表头的「(schema)」是误导。
- **R2** 系统名称带单位前缀（「XX公司系统A」这种写法）。
- **R3** 主键判重忽略大小写（inst1＝INST1；数据湖的小写表名＝源系统的大写表名），同键第一行进、其余报错；重复导入不报错。
- **R4** 「归属域」和可选列留空，与成功版一致。

关键点：**同事那份「部分成功」的文件价值最大**——它在同一个文件里对照了两种写法（一个 sheet 填 Schema 全败、另一个 sheet 填实例名成功），等于平台免费做了一次 A/B 实验。

## 12.08 万 → 11.73 万：删了什么

按「系统＋库＋表＋字段，忽略大小写」合并掉 3,519 行，三类来源：
1. 同一实例下两个 Schema（S1、S2）的同名表——平台主键里没有 Schema，只能合并；
2. 同一个实例名有大小写两种写法（inst1 / INST1），登记了同一批表字段；
3. 123 张数据湖副本表（小写英文名）与源系统表（大写）重复。

## AI 替用户补写 / 决定的内容（对外汇报里不写，修改说明里全有）

- 字段中文名：借同名英文字段在别处的中文名约 3.25 万个；无从借用、用英文名兜底约 1.78 万个。
- 表中文名：英文名兜底约 2 千张；备份表用「母表中文名＋备份」30 张；多种写法取多数 48 张。
- 123 张数据湖表并入源系统表，数据湖那一份没有单独登记。
- 业务域统一填一个值、描述＝中文名称、实例名统一小写、示例值乱码→「/」、文本清理约 4.3 万格。

## 遗留

- 原始资料缺中文名；清单里「提供方式」「接收部门」等必填整列空、枚举值不合规——交业务部门补。
- 数据湖表如何单独登记，需平台方给数据湖配数据源。
- 清单导入口的规则没有独立实测，按与元数据一致的原则处理。

## 如果重来一次

1. 开工第一句：「导入记录截个全表给我；以前谁传成功过、文件在哪？」——半小时就能对完账，而不是一个晚上。
2. 表头和成功样本冲突，信成功样本。
3. 探针单独交付，不给全量捷径。
4. 用户说「先别改了」，逐项确认撤哪条，保住前缀这种正确需求。
