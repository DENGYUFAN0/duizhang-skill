# 对账（往黑盒系统里导数据）

> 平台说了什么不重要，平台做了什么才重要。

模板表头、填写说明、同事口头说法都只是线索；平台自己的**导入记录、错误报告、曾经成功过的文件**才是唯一真相。任何关于「平台规则」的假说，必须能**精确复现**平台报出来的数字，否则就是还没找到规则。

来历：一次真实战役里，AI 按模板字面规则交了 5 版，平台 0 行成功；最后靠「导入记录 + 同事一份部分成功的文件」做数字对账，三组数字精确吻合，才发现表头写的「数据库名称(schema)」其实要填实例名、平台判重忽略大小写。复盘见 [references/case-study.md](references/case-study.md)。

## 五条铁律

1. **实况高于文档。** 表头、释义、填写说明和平台行为冲突时，以行为为准——哪怕表头白纸黑字写着 schema。成功样本怎么写就怎么写。模板自相矛盾时，别默认「写得最具体的那句对」。
2. **没有证据不动手。** 开工前先收齐第 0 步的证据。没看过导入记录就改规则，等于蒙眼改。
3. **假说必须对上数。** 用平台报过的数（总数、成功数、失败数、错误条数）检验每条假说：精确复现才算成立，两组以上独立数字同时吻合才算强证据。本地模拟「重复变少了」只能排除必败，证明不了能过。
4. **小样本先行，探针单独交付。** 未证实的规则先用几十行探针实测。探针只用本来就要导的真实数据（多数平台没有测试环境，能过的行真的会进生产）。探针和全量**不要同批给**——给了捷径，用户就会跳过探针直接传全量。
5. **改动面最小。** 只填必填列和平台查找要用的列，可选列留空；每多填一列就多一个被拒的理由。先让数据进去，再二次补充。

## 流程

### 第 0 步　收证（向用户要，要全）

1. **平台导入记录**全表截图，翻到有历史成功记录的那几页：文件名、时间、总数、成功数、失败数。
2. **最近一次失败的错误报告**：用平台的「导出」拿全量，不要只截首页——错误报告常按字符串排序（10、100、1000…）、列号被截断、两个 sheet 交错，首页会误导。
3. **任何曾经成功过的文件**：用户自己的、同事的、上一批次的。开口就问：「以前谁传成功过？用的哪个文件？」这一问比读十遍模板有用。
4. 空模板、填写说明、源数据；以及「全部行还是可见行」——别人给的 Excel 先体检：筛选、隐藏行列、公式与外部链接、表头在第几行、示例行、合并单元格。

用户手里没有这些时，告诉他去哪截、截什么，而不是开始猜。

### 第 1 步　比对「成功」与「失败」

- `scripts/combos.py`：把成功文件和失败文件在**查找列**（报错点名的那几列）上的取值组合列出来，看差集。差集往往一眼就是答案。
- `scripts/xlsxdiff.py`：对照两份文件的结构——sheet、表头行、公式、单元格类型、文本长度、隐藏字符。
- 报错里的列号是「参与查找的列集合」，不是出错的格子；它会把你引去改无辜的列。真正出错的列，用成功与失败样本在这组列上的差集来定。

### 第 2 步　数字对账

把平台的数字列成等式，找能**精确**复现它的解释。常用拆法：

| 等式 | 含义 |
|---|---|
| 失败数 = sheet1 全败行数 + sheet2 部分失败 | 导入记录的总数通常是各 sheet 之和，要自己拆 |
| 错误条数 − 失败行数 = 同时犯两种错的行数 | 差额往往就是重复行——它本身就是线索 |
| 成功数 = 按某口径去重后的唯一键数 | 反推平台的判重口径 |

`scripts/dupcount.py --target <平台数字>`：在多种口径（精确 / 去空白 / 忽略大小写 / 全半角归一）× 两种策略（先到先得 / 同键全拒）下数重复，标出恰好等于平台数字的组合。多个口径同时命中时，先取最简单的那个作为假说，再找能区分它们的样本。

### 第 3 步　假说表 + 探针

- 列一张假说表：规则 / 证据 / 复现了哪个数字 / 置信度（实证、强推断、推断）。
- 还没证实的规则用 `scripts/probe.py` 生成探针：每个待定列的候选写法做笛卡尔积，每种组合配一行**不同的**真实数据（主键不重复），附「行号 → 写法」对照表。单独交给用户，拿回错误报告后再生成全量。
- 探针也能试可选列、特殊字符、长度上限这类「第二层校验」。

### 第 4 步　按实测规则全量生成

- 只按假说表里「实证 / 强推断」的规则改，其余保持源数据原样。
- **按平台口径预去重，并由你决定留哪行**：平台忽略大小写，你就忽略大小写去重；平台先到先得，就只留最好的那行。留哪行要有写明的规则（例如：有真实中文名 > 与多数写法一致 > 有示例值），删掉的每一行记进修改说明。
- 标识类字段（英文表名、字段名）原样不动；描述类字段（中文名）缺失或乱码可按规则转写，但每处可追溯：同名借用 → 母表借用 → 英文名兜底，逐条记录。**转写出来的是推断，不是原文**，要在修改说明和汇报里分清。
- 清洗规则先拿真实样例写反例测试；改动量异常（比如一次改了四万多格）就停下查。
- 源文件被 WPS/Excel 占用时写新文件，不强关用户的程序；输出放独立目录、文件名带版本和日期。

### 第 5 步　自检：回放平台规则，而不是模板规则

- 自检以**平台实测规则**为纲：查找列取值是否全落在「已证实能过」的集合内；按平台口径主键是否唯一；行数是否等于预期成功数。
- 「按模板规则 50 项 36 项通过」≠「能上传」。结论必须带一行「范围：…；未覆盖：…」，没在平台实测过就写「未在平台实测」。
- 能用历史数字交叉印证的就印证（本案 v3 表数 = 某次历史成功数，字段数 = 另一次历史成功数）。

### 第 6 步　上传与回收

- 按依赖顺序：先元数据（表、字段），后清单（引用元数据的那张）。上传前把文件名改成带版本的名字——导入记录常常截断文件名、不记导入人。
- 上传后只认「已导入数量」这一列（0 行成功也可能显示绿色「完成 100%」），把总数 / 成功 / 失败抄进自己的上传台账。对不上就导出错误报告，回第 2 步。
- 重复导入通常是覆盖更新、不因「已存在」报错——但先用小批确认。

## 给执行本 skill 的 AI 的自律

都是真实犯过的错，细节见 [references/ai-pitfalls.md](references/ai-pitfalls.md)：

- **防回音室。** 你先提出的推断，经用户转述回来（「不是要填 schema 吗？」）不是外部证据。先分清这话来自平台证据、用户的领域知识，还是你自己之前说的；分不清就问：「这是平台要求，还是看表头推断的？」
- **用户的问句不是指令**，先摆证据再决定改不改。
- **先要导入记录和成功样本**，再动脑子；闭门推理两轮不如问一句「谁传成功过」。
- **需求台账。** 用户说「先别改了」时，逐项确认撤哪几条，别整包撤回把正确的需求也弄丢。
- **识别与修改分开交付**；有冲突的值只列出来，除非用户明说「你觉得哪个对就留哪个」——那时就给默认决策、理由和可回滚的记录，别再把球踢回去。
- **不静默纳入被筛选/隐藏的行，不说「完全一致」**，除非换了一条解析路径逐格比过。
- **涉及外部系统的教训等实测后再入账**；入账的教训被推翻了，回去改原条目。
- **对外文字（给领导的汇报）只写用户给过或平台证实的数**；压缩篇幅时别把「未证实」的限定词一起删掉。
